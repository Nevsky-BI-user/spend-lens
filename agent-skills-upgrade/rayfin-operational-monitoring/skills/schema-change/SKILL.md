# Зміна схеми БД — оркестрація

Схема автогенерує SQL БД + GraphQL (DAB); джерело коду застосунку з сервісу
відновити неможливо — репозиторій єдине джерело істини. Кроки нижче не
пропускати й не міняти місцями.

## 1. План проти інваріантів

Прочитати `.claude/rules/schema-db.md` і скласти план зміни, звіривши кожен
пункт:

- кожне `@text()` має `max` — без нього NVARCHAR(MAX): може зламати побудову
  GraphQL-схеми і знімає межу розміру запису;
- `exclude`/`include` цілять у КОЛОНКИ, не navigation properties: для FK —
  явне `@uuid() <name>_id` поруч із `@one(...)`;
- незмінні поля авторства/області (`user_email`, `user_id`, `organization`,
  `reporting_period`) виключені з update — політика перевіряє рядок, не payload;
- `delete` прибрано з УСІХ сутностей (soft-delete через
  `is_deleted`/`deleted_at`) — джерело: коментар у `rayfin/data/schema.ts` +
  `schemaPolicy.test.ts`; нову сутність створювати без delete-дії;
- системну таблицю `Users` не оголошувати — вона вбудована;
- деструктивні зміни (видалення сутності/поля, зміна типу,
  optional → обовʼязкове) позначити в плані ОКРЕМО — вони вмикають
  STOP-правило деплою (п.5).

Під час встановлення цього пакета додайте інваріант про `delete` до розділу
«Інваріанти схеми» в `.claude/rules/schema-db.md` — наразі він зафіксований
лише в коментарі схеми й тесті.

План показати користувачу: зміни схеми — з тих, що чекають на явне
«затверджую» на своїй гілці до merge.

## 2. Правка + читальні субагенти

Після редагування `rayfin/data/schema.ts` запустити послідовно:

1. субагент `schema-reviewer` (`.claude/agents/schema-reviewer.md`) — breaking
   changes, зачеплені select-списки/форми/типи/демо-мок;
2. субагент `security-auditor` (`.claude/agents/security-auditor.md`) —
   політики, незмінні поля, `max`, секрети, покриття тестами авторизації.

Обидва лише читають і повертають звіти. Критичні/високі знахідки виправити й
перезапустити відповідного агента до чистого звіту; середні — виправити або
явно зафіксувати рішення у відповіді користувачу.

## 3. Тести

```bash
npx vitest run src/__tests__/schemaPolicy.test.ts
```

а перед комітом — повні `npx tsc -b` і `npx vitest run` (правило CLAUDE.md).

## 4. Документація в тому ж коміті

`git diff --staged --stat` МУСИТЬ містити docs/data-model.md: таблиці з
полями/типами, розрахункові правила, mermaid-діаграма звʼязків і штамп
«Оновлено:» у шапці. Коміт без цього diff — незавершена робота: не комітити.

## 5. І лише тепер — викотка

Запропонувати скіл `deploy-checklist`. Ключове з нього повторити одразу:

- порядок: БД (`npx rayfin up` — виконує КОРИСТУВАЧ) → фронт
  (`npx rayfin up staticapp deploy`) → «Адміністрування → Довідники →
  Імпортувати», якщо зачеплено довідник;
- **STOP-правило**: хоч одна деструктивна зміна з п.1 → нічого не деплоїти,
  вивести перелік і чекати явного підтвердження користувача;
- після зміни політик — інспекція `rayfin/.temp/dab-config.json` після
  `db apply`: справжні колонки видно в `x-schema.fields` (тільки читання —
  файл згенерований).
