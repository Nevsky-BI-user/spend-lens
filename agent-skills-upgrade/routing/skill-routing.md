# Маршрутизація Power BI-скілів: дерево рішень

Це дерево вирішує головну скаргу: «скіли не спрацьовують коли треба, або спрацьовують коли не треба».
Воно закодоване у нових описах шести скілів (див. `../skills/`) і придатне для вставки
в CLAUDE.md проєктів та в персональні інструкції на claude.ai.

## П'ять питань (у цьому порядку)

```
1. Це review PR/diff І в репозиторії є PBIP-артефакти (*.pbip, *.pbir, *.pbism,
   *.tmdl, .SemanticModel/, .Report/)?
   ТАК → pbip-pr-reviewer          НІ (немає PBIP) → вбудований code-review

2. Результат — PNG-іконка / URL іконки (у т.ч. SWITCH-міра з URL-ами іконок)?
   ТАК → icon-set-manager

3. Результат — щось НАМАЛЬОВАНЕ?
   3а. Всередині комірки таблиці/матриці (спарклайн, бар у комірці, бейдж,
       progress ring, heatmap-комірка) → dax-svg
   3б. Окремий візуал на канві звіту (waterfall, small multiples,
       «зроби графік») → deneb-vegalite
   Немає жодного сигналу «комірка чи канва»? → одне уточнювальне питання,
   або за замовчуванням deneb-vegalite (канва — частіший намір).

4. Результат — числове/текстове значення міри: нова міра або НЕПРАВИЛЬНИЙ
   результат → dax-measures

5. Міра ПРАЦЮЄ, але ПОВІЛЬНО («гальмує», «повільно», «оптимізуй»,
   DAX Studio / Performance Analyzer) АБО потрібен refactor/читабельність
   без зміни логіки → dax-optimization
```

## Правила ексклюзивного володіння (пари, що конфліктували)

| Запит | Було (конфлікт) | Стало (власник) |
|---|---|---|
| «оптимізуй цю міру, вона гальмує» | dax-measures ↔ застарілий optimization-скіл (див. REPORT.md) | **dax-optimization** (dax-measures більше не claims «optimize») |
| голе «намалюй …» | dax-svg перехоплював усе | **deneb-vegalite** за замовчуванням; dax-svg — лише з контекстом комірки/таблиці |
| «намалюй спарклайн в таблиці» | dax-svg ↔ вбудований dataviz | **dax-svg** (додано «спарклайн», «графік в комірці») |
| «зроби heatmap / bullet» | dax-svg ↔ deneb-vegalite | **комірка → dax-svg; канва → deneb-vegalite** (перше речення обох описів) |
| «додай KPI» | 4 скіли | **значення → dax-measures; картка-візуал → deneb-vegalite; в комірці → dax-svg; іконка → icon-set-manager** |
| «зроби міру з іконкою по статусу» | dax-measures ↔ icon-set-manager | **icon-set-manager** (dax-measures отримав зворотну межу) |
| «ревью цього PR» у звичайному коді | pbip-pr-reviewer стріляв усюди | **code-review**; pbip-pr-reviewer — лише за наявності PBIP-файлів |

## Снипет для CLAUDE.md проєктів (вставити як є)

```markdown
## Маршрутизація скілів (Power BI)

Коли запит стосується Power BI, обирай скіл за деревом:
1. Review PR у PBIP-репо → `pbip-pr-reviewer`; в іншому репо → `code-review`.
2. PNG-іконка або URL іконки → `icon-set-manager`.
3. Намальоване в комірці таблиці/матриці → `dax-svg`; окремий візуал на канві → `deneb-vegalite`.
4. Нова міра або неправильний результат → `dax-measures`.
5. Міра правильна, але повільна, або потрібен refactor/читабельність без зміни логіки → `dax-optimization`.
Не викликай два скіли на один запит; за відсутності сигналу «комірка чи канва» — постав одне питання.
```

## Чому це працює (механіка тригерингу)

- Роутер бачить **лише frontmatter-описи** всіх скілів одночасно і обирає найкращий
  лінгвістичний збіг. Тому: тригерні фрази мають бути **дослівно ті, що ви друкуєте**
  (укр + англ), межі «Do NOT trigger» — за **наміром**, а не за ключовим словом,
  якого користувач ніколи не скаже («SVG» ніхто не пише — пишуть «спарклайн в таблиці»).
- Описи тримайте ≤ ~1024 символів: довші можуть обрізатися в маніфесті скілів.
- Один запит = один власник: кожна суміжна гілка дерева названа в сусідньому скілі.
- Скіли з побічними ефектами (деплой, PR-ритуали) — `disable-model-invocation: true`
  і виклик лише руками через `/skill-name`.

## Гігієна каналів (друга причина «не спрацьовує»)

Один і той самий скіл не повинен приходити в сесію **двома каналами** одночасно
(плагін `powerbi-craft` + копія в `~/.claude/skills` + synced з claude.ai):
роутер бачить два описи-конкуренти, і вибір стає лотереєю.

Правило: **одне середовище — один канал.**
- Claude Code локально: плагіни з marketplace (`claude plugin install ...@powerbi-craft`), копій у `~/.claude/skills` не тримати.
- claude.ai / хмарні сесії: набір синхронізованих скілів, оновлюваний з canonical-джерела.
- Canonical-джерело описів/тіл: `powerbi-craft-marketplace` (див. `../scripts/skill_drift_check.py` для контролю дрейфу).
